Rwanda Pharmacy Management Full Configuration Guide

Purpose: checklist and configuration reference required to make the Rwanda Pharmacy Management module work end to end.

1. Configuration Order

  1. Install and start required OpenMRS modules.
  2. Assign module roles and privileges.
  3. Configure global properties.
  4. Configure OpenMRS locations and location tags.
  5. Create pharmacy locations and link them to OpenMRS locations/tags.
  6. Configure supplier/RMS and pull all master product items first.
  7. Map master products to local items, concepts, drugs, programs, and material types.
  8. Configure billing mappings for drugs and consumables where billing is expected.
  9. Configure app framework links for pharmacy dashboard, lab request, general pharmacy request, consumable request, and prescription request.
  10. Configure SMS, SMTP, HIE, reports, and alerts as needed.
  11. Test each workflow using a real location, user role, patient, bill, and stock item.

5.2 Supplier Records

Create suppliers in Supplier Configuration. For RMS set API enabled. For non-RMS suppliers, set email address and leave API disabled if orders are sent by email.

5.3 First Product Master Pull

  1. Open Product sync.
  2. Authenticate to RMS if required.
  3. Pull all master product items before creating local items or purchase orders.
  4. Confirm each item has NPC code, name, material type, program, price, and active status.
  5. Remember that the same NPC can appear more than once when it belongs to different programs. Do not merge these records unless the program is also the same.

6. Pharmacy Locations and OpenMRS Location Tags

  1. Create one main pharmacy location and mark it as main store.
  2. Create each dispensing pharmacy.
  3. Link each pharmacy to an OpenMRS location and/or one or more OpenMRS location tags.
  4. If one OpenMRS location tag maps to more than one dispensing pharmacy, users will be asked to choose active pharmacy once per session.
  5. If one dispensing pharmacy serves multiple OpenMRS location tags, add all relevant tags to that pharmacy.
  6. Main-pharmacy-only navigation links are shown only when the logged-in OpenMRS location maps to the main pharmacy. Dispensing-only links are shown only when the location maps to at least one active dispensing pharmacy. Shared pharmacy pages require either mapping.

7. Billing Configuration

  1. Install and configure MOH Billing.
  2. Create facility services and billable services for drugs and consumables that should be billed.
  3. Map each billed drug/consumable concept to a facility service price.
  4. For prescriptions, drug billing mapping is checked through product drug concept and stocked local item concept/drug concept.
  5. Consumable order page loading does not check billing mappings. Billing mappings are validated when the order is submitted.
  6. Configure rwandapharmacymanagement.prescription.paymentBillMode as strict or latest.
The module creates and links its own prescription/consumable request records to billing. Avoid database triggers that also create drug billing rows from OpenMRS orders, because they can duplicate bills or fail when billing mappings contain duplicate rows.

Use Missing billing mappings to identify products that cannot be billed, and Link prescription bills when a request exists but the bill link needs administrative correction.

11.4 HTML Form Entry Pharmacy Order Tags

The module registers embedded HTML Form Entry tags when it starts. These tags let form builders add pharmacy ordering controls directly inside an HTML Form Entry form:

<rpmPrescriptionOrder />
<rpmConsumableOrder />

Optional attributes:

TagAttributeUse
rpmPrescriptionOrderrequired="true"Requires at least one prescription line before the HFE form can be saved.
rpmPrescriptionOrderpatientBillId="123"Links the created prescription request to a known patient bill ID.
rpmPrescriptionOrdertitle="..."Changes the embedded section title.
rpmPrescriptionOrderbuttonLabel="..."Changes the add-line button label.
rpmConsumableOrderrequired="true"Requires at least one consumable line before the HFE form can be saved.
rpmConsumableOrdertitle="..."Changes the embedded section title.
rpmConsumableOrderbuttonLabel="..."Changes the add-line button label.

On form save, the tags create Rwanda Pharmacy Management patient requests through the same prescription and consumable services used by the normal patient dashboard pages. Empty embedded order tables are ignored, so a form can include an optional order section without creating blank pharmacy requests.

Prescription orders require a patient, active visit, provider, and location. Consumable orders require a patient, location, and consumable billing readiness. Edit/delete of created lines remains in the normal pharmacy request workflows.

12. Operational Workflow Configuration

12.1 Prescription and Patient Queue

AreaConfiguration rule
OpenMRS drugsEach prescribed product must map to the correct OpenMRS Drug/concept. Remove duplicate active OpenMRS drugs with the same practical medication name to avoid ambiguous prescription behavior.
Dose instructionsDose instructions are mandatory on prescription entry. They are stored and shown as instructions, while dose unit is intentionally not shown on dispensing and is sent blank to HIE.
Repeat prescriptionsWhen the same active drug is prescribed again for the same patient, the module replaces/discontinues the active same-drug order before saving the new one so OpenMRS does not block repeat prescribing within 24 hours.
Hidden itemsItems hidden from requesters are treated as out of stock on prescription entry and cannot be dispensed from patient queue.
BillingPrescription requests must have billable service mappings unless the item is intentionally unbillable. Administrative linking is available through Link prescription bills.
UPID searchConfigure rwandapharmacymanagement.hie.patientIdentifierTypeUuid with the UPID patient identifier type UUID. Patient queue search can then match that identifier and the queue displays it in a UPID column.
Queue cleanupControl > Patient queue cleanup requires Task: rwandapharmacymanagement.manageSettings. It previews pending payment/pending dispense requests by date range and optional pharmacy, then marks confirmed matches as NOT_SERVED with a reason so they leave the patient queue.

12.2 HTML Form Entry Embedded Orders

AreaConfiguration rule
Module dependencyHTML Form Entry must be installed and started because the pharmacy module registers rpmPrescriptionOrder and rpmConsumableOrder as custom HFE tags.
Prescription tagUse <rpmPrescriptionOrder /> in an HFE form to add an embedded prescription section. On save, it creates OpenMRS drug orders and the pharmacy dispensing request through PrescriptionService.
Consumable tagUse <rpmConsumableOrder /> in an HFE form to add an embedded consumable section. On save, it creates consumable requests through ConsumableOrderService.
Optional sectionsLeave required unset or false to allow the HFE form to save with no pharmacy lines. Use required="true" when the form must contain at least one pharmacy line.
Follow-up changesEdits, deletes, payment checks, dispensing, and billing cleanup continue to be managed in the existing pharmacy request and patient queue pages after the HFE form creates the request.

12.3 Item Visibility and Batch Expiry Control

Control pageConfiguration and effect
Item visibility controlRequires Task: rwandapharmacymanagement.adjustStock. Hidden items are listed first for review, can be searched by item name/code, and are hidden from requester-facing selection/availability.
Batch expiry controlRequires Task: rwandapharmacymanagement.adjustStock and a current main pharmacy mapping. Main pharmacy users can update the expiry date for an existing batch number without changing quantity.
ReconciliationRequires Task: rwandapharmacymanagement.adjustStock and a current pharmacy mapping. Main and dispensing pharmacies can use it for controlled stock corrections with adjustment reason and audit trail.

12.4 Pharmacy Item Requests

Pharmacy item requests are user requests to a selected pharmacy. The queue is placed under the Dispensing navigation block, and history is available with PDF download per request.

FeatureConfiguration rule
Requester pageRequester selects one pharmacy, then adds visible/requestable items. One request should not mix source pharmacies.
QueueQueue uses the user's active pharmacy and issues stock only from that pharmacy.
HistoryUsers with transfer or approval privilege can view request history and download a PDF copy of a request.

12.5 Main, Dispensing, and Department Transfers

WorkflowConfiguration rule
Main to dispensingRequires a main store, dispensing pharmacies, Head of Finance approval privilege, and transfer privilege. Review shows requesting pharmacy current quantity, previous info, removable request lines with reason, and multi-batch allocations when serving.
Transfer approval scopePharmacy transfer approval is restricted to the request's supplying pharmacy. Users only see and can approve/reject requested transfers where their current main or dispensing pharmacy is the transfer source.
Dispensing to dispensingSource excludes main pharmacy and the current active pharmacy. The receiving pharmacy is the active pharmacy.
Return to mainMain pharmacy initiates return request; selected dispensing pharmacy approves transfer back or rejects.
Transfer PDFsTransferred requests can be downloaded as PDF from transfer history/review pages.
Multi-batch transferThe transfer form can allocate one requested line across more than one source batch. Validation should compare the sum of allocations with requested/approved quantity, not each batch allocation against the full line quantity.

12.6 Department Store Workflows

Department workflows are controlled by Task: rwandapharmacymanagement.departmentStore for the department workspace. The current configuration avoids user-to-department assignment; access is role/privilege based.

PageUse
Department store workspaceSingle workspace for department users to request from pharmacy, view department stock, issue internally, and access request PDFs.
Department bulk requestDepartment requests items from pharmacy. The request page can autofill from dispensed items when full visibility exists, but values remain editable.
Department finance approvalFinance reviews department requests before pharmacy dispensing when workflow mode requires finance approval.
Department pharmacy dispensePharmacy dispenses approved department requests from the active dispensing pharmacy only. Batch choices must come from that dispensing pharmacy, not main pharmacy.
Department stock issueDepartment users can issue more than one internal item at the same time from department stock.

The department workflow mode global property is initialized to periodic accountability. Review workflow expectations before go-live.

12.7 Supplier, Delivery, and Purchase Order Controls

AreaConfiguration rule
Purchase order cartMain pharmacy users add items from stock/product view. Orders are grouped by program and supplier.
ApprovalHealth Facility Leader privilege approves or rejects purchase orders. Approved orders can be dispatched by API or email depending on supplier setup.
Main-only supplier pagesPurchase orders, supplier configuration, product sync, price history, and delivery receiving are main-pharmacy workflows and should only be visible when the current OpenMRS location maps to the main pharmacy.
Delivery receivingMain pharmacy receives from RMS/API order details, uploaded supplier template, or direct entry. Receipt proof PDF is available after successful receipt.
Supplier templatesTemplates contain example format rows and support blank/N/A expiry for items configured not to require expiry.

12.8 Reports and Exports

ReportConfiguration rule
Pharmacy stockRequires active pharmacy locations and current inventory balances.
Overall hospital stockSums stock across pharmacy locations. Main-pharmacy scoped in navigation.
Inventory movementRequires stock transactions. Used to audit received, issued, adjusted, and transferred quantities.
Item movementShows one item across one or all pharmacies, including batch, expiry, received, issued, balance, and months of stock. Patient dispense movements are stock transactions; new patient dispense rows store the dispensing request id in reference_number.

13. Alerts Dashboard Configuration

The Alerts Dashboard contains two separate alert tables: Expiration Alerts and Stockout and Low Stock Alerts. Both tables support filters and PDF export.

13.1 Expiration Alerts

Expiration alerts are calculated at batch level from current inventory balances.

Setting/filterUse
Pharmacy locationOptional. When selected, only batches in that pharmacy are shown. When blank, batches from all pharmacy locations are shown.
Item name/codeOptional item search.
CategoryOptional item category filter.
Expiry Alert DaysLooks forward from today. A value of 90 shows expired batches and batches expiring in the next 90 days.
Expiry statusCan show all expiry alerts, expired only, or expiring soon only.

Only batches with positive quantity on hand and an expiry date are included.

13.2 Stockout and Low Stock Alerts

Stockout and low stock alerts are calculated at item/location level when a pharmacy location is selected, and at whole-hospital item level when no location is selected.

Setting/filterUse
Pharmacy locationOptional. When blank, the report sums stock and consumption across the whole hospital.
Days of Stock Alert DaysThreshold for Low Stock. Example: 14 means alert when current stock is expected to last 14 days or less.
Consumption Lookback DaysNumber of past days used to calculate average daily consumption. Default is 90.
Stock statusCan show stockout and low stock together, stockout only, or low stock only.

The table only considers items that have ever had inventory activity: an inventory balance row or a stock transaction. It does not list every item in rpm_item.

average daily consumption = consumed quantity during lookback / consumption lookback days
days of stock = current quantity / average daily consumption

Items with current quantity of zero or less are shown as Stockout. Items with positive stock and days of stock less than or equal to the threshold are shown as Low stock.

13.3 PDF Export

The Download PDF button exports both alert tables using the same filters selected on the page.

select patient_dispensing_request_line_id, patient_dispensing_request_id, line_status

where patient_dispensing_request_id = <REQUEST_ID>;

15.4 Duplicate patient dispense check

select dr.patient_dispensing_request_id,
       dr.dispense_record_id,
       dr.date_created,
       dr.creator,
       dr.dispensing_pharmacy_location_id,
       drl.dispense_record_line_id,
       drl.item_id,
       drl.quantity_dispensed,
       drl.batch_number
from rpm_dispense_record dr
join rpm_dispense_record_line drl
  on drl.dispense_record_id = dr.dispense_record_id
where dr.patient_dispensing_request_id = <REQUEST_ID>
  and dr.voided = 0
  and drl.voided = 0
order by dr.date_created, dr.dispense_record_id;

15.5 Inventory by item and pharmacy

select i.name, b.pharmacy_location_id, b.batch_number, b.expiry_date, b.quantity_on_hand
from rpm_inventory_balance b
join rpm_item i on i.item_id = b.item_id
where i.code = '<NPC_CODE>' and b.voided = 0;

16. Final Go-Live Test Script

  1. Login as administrator and verify global properties, roles, app links, and locations.
  2. Pull master products and prices from RMS.
  3. Create or verify local items for one drug and one consumable.
  4. Receive stock into main pharmacy.
  5. Transfer stock from main to dispensing through approval.
  6. Create a prescription for a patient with an active visit and test SMS/logs if enabled.
  7. Pay or link the patient bill and confirm the patient queue updates.
  8. Dispense the prescription.
  9. Create a consumable request and confirm it appears in queue even if mapping is missing.
